# T16B — Ontology

## Method

RAG + web (2026-08-02); depth normal.

## Findings

- `CLAIM` [E2/E3] **Principles** = strategic “why / how to reason” with flexibility on how; **standards** = specific, little-flexibility requirements. Both needed; too many standards stifle; too few principles → chaos. [E2/E3: archman-dev architecture-principles-and-standards; dmccreary/atam — accessed 2026-08-02]
- `CLAIM` [E3] Principles ≠ standards: “write secure code” vs checkable allowlist validation — verifiability is the cut. [E3: pandorian.ai engineering standards — discovery]
- `CLAIM` [E2] Engineering values (ways of working) vs architectural principles (technical philosophy) as paired continuity artifacts (“aligned autonomy”). [E2: Pete Hodgson — https://blog.thepete.net/blog/2021/01/18/engineering-values-and-architectural-principles/]
- `CLAIM` [E2] XP: coding standards improve communication under collective ownership; should not constrict creativity. [E2: Alexandria `software_engineering` chunk_id=`33b1067eee2c779641678ac3`]
- `INFERENCE` [E4] Toolbelt vocabulary lean (validate in design):

| Term | Altitude | Checkable? |
|------|----------|------------|
| Principle | Philosophy / tone / core continuity | Softly — “decision upholds X?” |
| Standard | Concrete host rule | Yes — evidence/locator |
| Convention | Habitual naming/layout | Often yes (lint/sample) |
| Guideline | Prefer; waive easily | Weak |
| ADR / design accept | Locked decision | Yes — path+status |

- `GAP` No single ISO ontology — product must pick thin glossary.
